# US-04 — Implementación, demostración y límites

Implementación final del Punto 3, 10 de noviembre de 2026. Sin dependencias
externas, commits ni modificaciones del código protegido. B1 es evidencia
histórica; los contratos pendientes de banco y persistencia ya están implementados.

## Arquitectura

`cmd/interactive` → `cli.EjecutarPersistente` → `banco.Operador` → `persistencia.Archivo`.
El flujo anterior `cli.Ejecutar` permanece intacto y se usa con `-memoria`.

- Banco: céntimos int64, validación decimal, rechazo sin movimiento,
  UUID-like IDs aleatorios de 128 bits con crypto/rand (sin formato UUID),
  fechas UTC, secuencia, idempotencia, copias defensivas y mutex por servicio.
- Persistencia: un único documento lógico con saldo y transacciones. Almacenamiento
  físico compuesto por JSON visible, diario de confirmación y archivo de bloqueo.
- CLI: consulta, retiro, abono, historial y salida. Titular y saldo se solicitan
  solo en la primera ejecución; reiniciar no reemplaza la cuenta existente.
- Los .feature son documentales: no se instaló ejecutor Gherkin.

## Protocolo de confirmación

1. El servicio construye una copia candidata con saldo e historial juntos.
2. El adaptador verifica invariantes y que el candidato extienda exactamente
   en una transacción al estado anterior, sin alterar el prefijo del historial.
3. Anexa al diario una línea JSON con el documento completo y SHA-256, escribe,
   ejecuta Sync y cierra. No se reescribe ni borra el diario confirmado.
4. Escribe el JSON visible en un temporal del mismo directorio, sincroniza y
   cierra. Usa ReplaceFileW en Windows si el destino existe; Rename solo para
   la primera publicación. La corrección de recuperación NO depende de que
   estas operaciones de publicación sean atómicas.
5. Solo devuelve éxito tras confirmar diario y publicación. Si falla después de
   comenzar una escritura, devuelve ErrIncierto y bloquea nuevas operaciones.
6. Al reabrir, valida diario, suma, cadena de saldo, secuencia, IDs, moneda y
   resultados. Si el JSON visible es una versión anterior reconocida o falta,
   lo reconstruye desde el último registro completo. Si está corrupto, no lo
   sobrescribe silenciosamente: devuelve ErrCorrupto.
7. Un diario parcial, un JSON válido ajeno al diario o estados ambiguos bloquean
   el arranque. No se trunca ni elimina evidencia automáticamente.

Un fallo incierto puede haber confirmado el movimiento. Reabrir y consultar el
historial antes de volver a solicitarlo. La API permite reintentar con el mismo ID;
el CLI imprime el ID en un error, pero no ofrece un comando de reenvío de ese ID.
IDs repetidos con entradas textuales distintas son conflictos, incluso si las
entradas representan el mismo número (por ejemplo 1.0 y 1.00).

Un fallo antes de poder abrir el diario se comunica sin éxito. No se promete
registrar un intento si el medio de auditoría no está disponible.

## Exclusión y plataforma

Windows: CreateFileW abre `.lock` con modo compartido cero y conserva el handle
hasta Cerrar. Dos procesos no pueden abrir ese mismo archivo; al terminar el
proceso Windows libera el handle. El archivo puede permanecer y no debe borrarse
como forma de liberar un bloqueo. Se probaron exclusión y reapertura reales.

La persistencia de esta entrega está implementada y verificada solo en Windows;
otras plataformas devuelven un error explícito. El código bancario sigue siendo
independiente de Windows. Usar una ruta local y la misma ruta para todos los
escritores; no se garantizan alias por enlaces, unidades remotas o sincronizadores.
El mutex del servicio no coordina dos servicios sobre un adaptador compartido:
debe existir un operador por Archivo.

Fuentes oficiales consultadas:
- [Go: Rename](https://go.dev/pkg/os/#Rename), sin garantía atómica en no Unix.
- [Microsoft: ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew),
  estados de fallo y REPLACEFILE_WRITE_THROUGH no soportado.
- [Microsoft: apertura y uso compartido](https://learn.microsoft.com/en-us/windows/win32/fileio/creating-and-opening-files).

## Límites explícitos

- No se ha demostrado durabilidad ante corte eléctrico, fallo del disco o cachés
  del hardware. Sync no permite prometer esa garantía completa.
- Se ensayó terminación real del proceso antes y después del reemplazo, no un
  corte eléctrico ni todos los fallos internos posibles del sistema de archivos.
- SHA-256 detecta corrupción accidental; no autentica registros contra manipulación.
- El diario guarda estados completos: ocupa espacio creciente y no tiene compactación.
  La solución es adecuada para el laboratorio, sin promesas de escala.
- Respaldar JSON y diario juntos con el programa cerrado. No editar ni copiar
  solo el JSON para restaurar un respaldo cuando existe un diario de otra versión.
- El programa no sobrescribe archivos corruptos ni repara automáticamente diarios
  parciales. Requieren diagnóstico y recuperación manual desde una copia válida.
- `go test -race ./...` no pudo ejecutarse: compilador C sin soporte de 64 bits;
  el comando también activa las advertencias originales de vet.

## Demostración

```powershell
go run ./cmd/interactive -datos "$env:TEMP\demo-us04\estado.json"
```

Primera ejecución: titular Alice y saldo 100.00. Retirar 30.00, abonar 25.00,
consultar historial y salir. Volver a ejecutar con la misma ruta: debe mostrar
95.00 PEN y las dos transacciones. Consultar historial con opción 4.
Para rechazos: retirar 120.00, abonar 0 o ingresar abc; saldo permanece 95.00.
Para el flujo anterior: `go run ./cmd/interactive -memoria`.
Para el programa original del profesor: `go run .`.

La ejecución manual automatizada en dos procesos independientes produjo 95.00 PEN
y conservó exactamente los dos registros. Todos los datos de verificación se
generaron en directorios temporales, sin datos bancarios reales.

Los archivos laterales son `estado.json.journal` y `estado.json.lock`. El patrón
actual de .gitignore excluye data/*.json, pero no esos laterales; no agregarlos
a Git. No se modificó .gitignore.

## Evidencias de pruebas

Go 1.27.3 windows/amd64. Se usó GOCACHE temporal por la restricción de acceso a
la caché habitual, sin cambiar go.mod ni configuración persistente del entorno.

| Comando | Resultado |
|---|---|
| go build ./... | Código 0 |
| go test -vet=off -count=1 ./... -v | 32 funciones Test aprobadas, incluida 1 auxiliar de subprocesos; 31 pruebas principales de comportamiento |
| go vet ./... | Código 1, solo las seis advertencias originales de Println |
| go test -race ./... | Código 1, compilador C de 64 bits no disponible y vet original |
| git diff --check | Sin errores |

Distribución: headers 3, banco 10, CLI 9, persistencia 10 (incluye auxiliar).
Las diez pruebas de los puntos 1 y 2 permanecieron sin cambios y aprobaron.
Pruebas relevantes de persistencia: registro/reinicio/idempotencia; corrupción;
exclusión dentro y entre procesos; terminación antes/después de publicación;
fallo de reemplazo; diario parcial; error de escritura y ruta inválida.

Pruebas CLI: integración persistente con éxito/rechazo/reinicio/historial y ausencia
de falso éxito ante confirmación incierta. Banco mantiene sus casos de exactitud,
validaciones, concurrencia e idempotencia. Gherkin corresponde a estos comportamientos,
pero no se ejecuta como suite de pasos.
